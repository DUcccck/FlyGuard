# FlyGuard 🪰 — детектор атак на основі мозку дрозофіли

Прототип, який «нюхає» логи FortiWeb нюховою схемою мухи (грибоподібне тіло)
і знаходить шкідливі запити, зокрема ті, що FortiWeb **пропустив**.

## Як це влаштовано

| Муха | FlyGuard |
|---|---|
| ~50 типів нюхових рецепторів | 50 «каналів» запиту: SQL-ключові слова, `../`, `<script>`, ентропія, user-agent, частота запитів з IP, 4xx-ратіо тощо (`features.py`) |
| Проєкційні нейрони ON/OFF | відхилення каналу від норми вгору / вниз |
| 2000 клітин Кеньона, кожна слухає ~6 входів | розріджена випадкова проєкція |
| APL-нейрон (гальмування) | winner-take-all: активні лише 5% KC |
| MBON новизни | сила збудження KC: незвичний «запах» збуджує сильно |
| Дофамін → MBON «уникати» | KC, активні на запитах, які FortiWeb заблокував, асоціюються з небезпекою |

Наукова основа: Dasgupta et al., *Science* 2017 (FlyHash); Dasgupta et al., *PNAS* 2018 (детектор новизни мухи).

## Встановлення

```bash
pip install -r requirements.txt   # numpy, scikit-learn
```

## Швидкий старт на тестових даних

```bash
python -m flyguard sample                                   # 21 тис. синтетичних логів FortiWeb
python -m flyguard evaluate data/sample_fortiweb.log --truth data/sample_truth.txt
```

Результат на синтетиці (тест — друга половина доби):

| Модель | ROC-AUC | Recall @ 1% FPR | Знайдено атак, які FortiWeb пропустив |
|---|---|---|---|
| Муха: лише новизна (без міток) | 0.999 | 0.989 | 98% |
| Муха: новизна + дофамін FortiWeb | 0.998 | 0.950 | 91% |
| Isolation Forest (базова лінія) | 0.998 | 0.979 | 97% |

⚠️ Синтетичні атаки «легкі». Справжня перевірка — тільки на ваших логах.

## Основний режим: FortiWeb шле syslog напряму у FlyGuard

```
FortiWeb ──syslog──► FlyGuard (listen) ──► alerts.jsonl, blocklist.txt, CLI для FortiWeb
                          └──(опційно) пересилання тих самих логів у ваш SIEM
```

### Крок 1. Запустити FlyGuard на Linux-сервері
```bash
pip install -r requirements.txt
echo "203.0.113.10   # IP офісу / моніторингу — ніколи не блокувати" > whitelist.txt
python -m flyguard listen --udp 5140 --tcp 5141
#   + --forward 10.0.0.5:514   щоб логи йшли далі й у ваш SIEM
```
- **Моделі ще немає → режим навчання.** FlyGuard просто записує логи у `fortiweb_raw.log`.
  Після `--learn` запитів (за замовчуванням 200 000) муха навчається сама і вмикає режим захисту.
  Бажано, щоб за цей час набралося хоча б кілька днів звичайного трафіку. Для малого сайту зменште `--learn`.
- **Модель є (`model.npz`) → одразу режим захисту.**
- Щоб перенавчити: зупиніть сервіс, видаліть `model.npz` або запустіть `python -m flyguard train fortiweb_raw.log`.
- Порт 5140 обрано, бо порти нижче 1024 потребують root. Відкрийте його у файрволі лише для IP FortiWeb.
- **При великому трафіку краще TCP:** UDP-пакети на пікових навантаженнях можуть губитися.
- Щоб працювало постійно: `flyguard.service` (systemd), інструкція всередині файлу.

### Крок 2. Налаштувати FortiWeb
Назви пунктів меню можуть трохи відрізнятися залежно від версії прошивки.
1. **Log & Report → Log Policy → Syslog Policy → Create New**: IP сервера FlyGuard, порт `5140` (UDP) або `5141` (TCP).
2. **Log & Report → Log Config → Global Log Settings**: увімкнути *Syslog*, вибрати створену політику,
   рівень `information`. Увімкнути надсилання **attack** і **traffic** логів.
3. **Traffic log обов'язковий.** Без нього муха бачить лише те, що FortiWeb вже вважає атакою, а пропущені атаки залишаться поза увагою.
   Перевірте, що traffic logging увімкнено (*Log Config → Other Log Settings* та/або в server policy).

У CLI це команди `config log syslog-policy` і `config log syslogd`, див.
[log syslog-policy](https://docs.fortinet.com/document/fortiweb/7.6.6/cli-reference/852365) та
[log syslogd](https://docs.fortinet.com/document/fortiweb/7.6.3/cli-reference/172335).

### Крок 3. Перевірка
У консолі FlyGuard має з'явитися `[LEARN] зібрано 5000/...`. Якщо нічого немає, перевірте:
```bash
sudo tcpdump -n -A -i any port 5140 | head
```
Має бути видно рядки на кшталт `date=... type=traffic ... http_url="..."`.

## Веб-інтерфейс

Запускається разом з `listen` на `http://127.0.0.1:8080` (лише локально). Логін `admin`, пароль задається через
`--web-password` або змінну `FLYGUARD_WEB_PASSWORD`. Якщо пароль не задано, FlyGuard генерує його і друкує в консоль.

Що в ньому є:
- **Режим і прогрес навчання.** Кнопка «Навчити зараз» запускає навчання, не чекаючи ліміту `--learn`.
- **Лічильники і графіки** запитів та алертів за хвилину за останню годину.
- **Кандидати на блокування.** Для кожного IP: поріг ризику, причини («чому») і приклад запиту.
  Дії:
  - **Підтвердити** — IP потрапляє у файл `blocklist.approved.txt` і в CLI-експорт;
  - **Хибна тривога** — IP прибирається зі списку;
  - **У білий список** — IP назавжди записується у `whitelist.txt`.
- **Останні алерти** з фільтром за IP або URL, а також **Топ IP**.
- **Панель «Мозок мухи»** праворуч показує, як муха обробила запит, у 4 кроки:
  1. **50 нюхових рецепторів.** Ознаки запиту, порівняні з нормою: червоні вище норми, сині нижче.
  2. **2000 клітин Кеньона.** Видно, які 100 клітин (5%) спалахнули і хто з рецепторів їх збудив.
     Колір клітини означає, з чим вона асоціюється: з атаками чи з нормальним трафіком.
  3. **Вихідні нейрони.** Новизна («незнайомий запах»), небезпека (пам'ять дофаміну) і підсумковий ризик із позначкою порогу.
  4. **Рішення:** тривога чи норма.

  За замовчуванням панель показує останній запит наживо. Клік на рядок в «Останніх алертах» показує саме цей алерт.
- **Вкладка «🧠 Мозок мухи»** (перемикач угорі) показує спрощену анатомічну схему мозку дрозофіли, вигляд спереду.
  На ній видно, як зараз проходить сигнал:
  - антени;
  - антенальні частки (50 гломерул = 50 ознак запиту);
  - проєкційні нейрони;
  - чашечка грибоподібного тіла (по 1000 клітин Кеньона в кожній півкулі);
  - APL-гальмування;
  - α/β-частки з MBON новизни та небезпеки;
  - дофамінові нейрони;
  - рішення.

  Потоки анімовані, а їхня сила залежить від сигналу. Оновлення кожні 1,5 с.
  Зорові частки й латеральний ріг показані для анатомії, але FlyGuard їх не використовує.
- **Налаштування:**
  - повзунок порогу ризику (діє одразу);
  - перенавчання моделі;
  - завантаження CLI для FortiWeb: лише підтверджені IP або всі кандидати.

**Доступ з мережі — через nginx.** FlyGuard не змінюється: він слухає лише 127.0.0.1:8080, а назовні
його віддає nginx за адресою `https://<IP-сервера>/`. Готовий конфіг — `nginx/flyguard.conf`:
HTTPS, переадресація з http, доступ лише з внутрішніх мереж (10/8, 172.16/12, 192.168/16, 100.64/10),
обмеження 5 запитів/с з одного IP проти підбору пароля.
```bash
sudo apt install -y nginx            # або: sudo dnf install -y nginx
sudo mkdir -p /etc/nginx/ssl
sudo openssl req -x509 -newkey rsa:2048 -nodes -days 825 \
  -keyout /etc/nginx/ssl/flyguard.key -out /etc/nginx/ssl/flyguard.crt \
  -subj "/CN=FlyGuard" -addext "subjectAltName=IP:<IP-сервера>"
sudo chmod 600 /etc/nginx/ssl/flyguard.key
sudo cp nginx/flyguard.conf /etc/nginx/conf.d/flyguard.conf
sudo nginx -t && sudo systemctl enable --now nginx && sudo systemctl reload nginx
```
На Ubuntu/Debian, якщо порти 80/443 зайняті сайтом за замовчуванням, вимкніть його:
`sudo rm /etc/nginx/sites-enabled/default`. У файрволі відкрийте 443/TCP (і 80/TCP для переадресації)
лише для внутрішніх підмереж; порт 8080 відкривати не потрібно.
Вимкнути інтерфейс: `--web-port 0`.


## Check Point Quantum Spark

FlyGuard також розуміє syslog Check Point у форматі `[key:"value"; key:"value"; ...]`.
Цей формат Spark надсилає за замовчуванням, і змінити його на Spark не можна.
- **Що використовується:** записи з полем `resource` (повний URL). Їх дають URL Filtering, Application Control та IPS/Threat Prevention.
  Звичайні записи про з'єднання без URL (Firewall Accept/Drop) пропускаються.
- **Мітка «атака» для навчання:** `action` = Drop / Reject / Block / Prevent / Redirect, або є поле `attack` / `protection_name`.
- **HTTPS:** щоб бачити шлях і параметри HTTPS-запитів, на Spark має бути увімкнена HTTPS Inspection.
  Без неї видно лише домен.
- **Окремий екземпляр.** Spark здебільшого бачить вихідний трафік користувачів, а FortiWeb — вхідний трафік до сайту.
  Тому для Spark краще запустити окремий FlyGuard (своя тека, порти і модель), щоб не змішувати «запахи».


## Модулі: FlySOAR, FlyBAS, FlyHoney

У веб-інтерфейсі ліворуч є розділи. Крім «Панель» і «Мозок мухи»:

- **⚡ FlySOAR — рефлекси.** Плейбуки «якщо ризик ≥ X і тривог ≥ Y → сповістити / заблокувати».
  За замовчуванням усі блокування чекають вашого схвалення. Автоблок працює лише з TTL
  (блок сам знімається) і з лімітом на годину. Сповіщення — у Telegram.
- **🎯 FlyBAS — муха-розвідник.** Безпечна симуляція атак проти вашого застосунку за WAF:
  муха шле тестові атаки, FlyGuard має їх виявити. Результат — табель «надіслано/виявлено»
  і карта покриття за MITRE ATT&CK. Ціль лише внутрішня (allowlist), запуск вручну.
- **🍯 FlyHoney — пастки.** Фальшиві порти-сервіси. Будь-яке з'єднання — майже напевно атака,
  бо легітимний користувач туди не ходить. Спіймані IP подаються у FlySOAR.
- **🔌 Інтеграції.** FortiGate, FortiWeb, Check Point для блокування IP. За замовчуванням
  dry-run: нічого не змінюється, лише показується готова дія/CLI. Реальне застосування —
  тільки коли ви увімкнете інтеграцію. Налаштування зберігаються у config.json (права 600).

Усе це керується з веб-інтерфейсу; у config.json лежать плейбуки, цілі BAS, порти пасток і доступи.


## Дві мухи: веб і мережа

FlyGuard тепер аналізує і HTTP-запити, і звичайні мережеві з'єднання — тобто **весь трафік**.

- **Веб-муха** (як раніше): логи FortiWeb / Check Point з URL. Ловить SQL-ін'єкції, XSS, сканування шляхів тощо за вмістом запиту.
- **Мережева муха** (нове): логи з'єднань Check Point / FortiGate без URL (`src`, `dst`, порт, дія, зони).
  Ловить **сканування портів** (одне джерело перебирає багато портів), **sweep** (одне джерело по багатьох адресах),
  аномальні з'єднання і незвичні сплески. Навчається без міток: норма — ваш звичайний трафік.

Обидві працюють одночасно в одному процесі. Кожен запис автоматично йде до потрібної мухи:
є URL — до веб-мухи, звичайне з'єднання — до мережевої. Алерти, кандидати на блокування і FlySOAR спільні.

Моделі зберігаються у двох файлах: `model.npz` (веб) і `model_net.npz` (мережа). Під час навчання
створюються обидві — та, для якої є достатньо даних (веб: ≥ 50 HTTP-запитів; мережа: ≥ 200 з'єднань).
Тому навіть якщо FortiWeb не шле traffic-логи, мережева муха все одно працюватиме на логах Check Point.

**Навчання кожної мухи — незалежне.** У кожної свій лічильник, своя ціль (`--learn`; для мережі
можна окремо через `--learn-net`, якщо задано) і свій момент старту. Мережева муха переходить у
режим захисту, щойно набере свої з'єднання, **не чекаючи** HTTP-трафіку, і навпаки. Якщо спроба
навчання зірвалась (замало даних) — вона повторюється автоматично, коли надійде ще стільки ж
записів (муха не «застрягає» в навчанні). У веб-інтерфейсі в карті «Мухи вчаться…» кожна має
власну смужку прогресу, і рядок зникає, щойно ця муха готова.

### Вибір мухи у веб-інтерфейсі

- У лівому меню розділ **«Мозок мухи»** має дві вкладки з іконками: **🪰 Веб-муха** і **🕸️ Мережева муха** —
  так можна обрати, чий мозок дивитися. Біля «Мережева муха» стоїть позначка: `✓` коли вона навчена, `off` — поки ні.
- У вкладці «Мозок мухи» та на бічній панелі «Панель» угорі є перемикач **🪰 Веб-муха / 🕸️ Мережева муха** —
  анатомічна схема підписана, чия вона, і показує саме ту кількість ознак (веб — 50, мережа — 25).
- На «Панелі» під вкладками з'явився фільтр **Муха: Всі / 🪰 Веб / 🕸️ Мережа** — відбирає кандидатів і алерти
  потрібної мухи. Клік на мережевий алерт автоматично перемикає «мозок» на мережеву муху.

## Робота з файлами логів (без syslog)

### 1. Експорт
Підходить будь-який з форматів:
- **Syslog / raw** (`date=... time=... type=attack src=... http_url="..."`) — з FortiAnalyzer, syslog-сервера або *Log & Report → Download*;
- **CSV** з заголовками;
- **JSON / JSON Lines** (ELK, Wazuh, Splunk) — вкладені поля розгортаються автоматично.

Потрібні **і attack-, і traffic-логи** (traffic logging має бути увімкнено в політиці),
бажано хоча б за кілька днів. Якщо назви полів інші — додайте їх до `ALIASES` у `parsers.py`.

### 2. Оцінка
```bash
python -m flyguard evaluate my_fortiweb.log
```
Без `--truth` еталоном вважаються рішення FortiWeb. Тоді метрики показують, наскільки муха
«згодна» з FortiWeb, а найцікавіше — алерти на запити з `action=Accept`.

### 3. Навчання і потоковий режим
```bash
python -m flyguard train my_fortiweb.log -o model.npz            # з мітками FortiWeb
python -m flyguard train my_fortiweb.log -o model.npz --unsupervised   # лише «нюх новизни»

python -m flyguard guard new_logs.log -m model.npz                # dry-run
tail -F /var/log/fortiweb.log | python -m flyguard guard - -m model.npz --follow
```
Що отримаєте:
- `alerts.jsonl` — кожен підозрілий запит з поясненням (`why`: які канали «пахнуть» незвично);
- `blocklist.txt` — IP, що набрали `--min-hits` підозрілих запитів;
- `blocklist.txt.fortiweb.txt` — готовий фрагмент CLI (`config waf ip-list` з `black-ip`).
  **Переглянути вручну** й застосувати до IP List-політики FortiWeb.
  Синтаксис перевірте для своєї версії прошивки FortiWeb.

Налаштування: `--threshold` (поріг ризику 0..1), `--min-hits`, `train --fpr` (допустима частка хибних алертів).
На синтетиці `--min-hits 2 --threshold 0.95` заблокував 104 із 119 атакуючих IP і 2 легітимні.

## Рекомендований шлях впровадження

1. **Тиждень у тіні.** Лише `alerts.jsonl`, аналітик переглядає. Дивимося на хибні спрацювання.
2. **Ручний blocklist.** Аналітик застосовує згенерований CLI.
3. **Авто-блок із TTL.** Через REST API FortiWeb, з білим списком (свої IP, моніторинг, партнери)
   і автоматичним зняттям блоку через N годин.
4. **Етап 2 — справжній коннектом.** Замінити випадкову матрицю PN→KC на реальні зв'язки
   з FlyWire (PN → KC з нюхової частки) і порівняти з поточною версією.

## Обмеження
- Модель вчиться на «нормальному» трафіку. Якщо в навчальних даних уже є непомічена атака,
  муха вважатиме її нормою.
- Детектор новизни ловить **незвичне**, а не обов'язково шкідливе: релізи, нові API та
  маркетингові кампанії теж дадуть алерти. Перенавчайте після змін на сайті.
- Дофамінове навчання від FortiWeb копіює і його помилки.

## Структура проєкту

```
flyguard/            — Python-пакет (ядро)
  fly.py             — грибоподібне тіло (KC, APL, MBON, дофамін)
  features.py        — ознаки веб-запитів і мережевих з'єднань (дві мухи)
  parsers.py         — парсери логів FortiWeb / Check Point / CSV / JSON
  listener.py        — syslog-приймач, детектор, навчання, App
  web.py             — веб-інтерфейс (лише стандартна бібліотека)
  web_index.html     — односторінковий UI
  soar.py            — FlySOAR (плейбуки, черга дій, TTL)
  bas.py             — FlyBAS (безпечна симуляція атак, MITRE)
  honeypot.py        — FlyHoney (пастки)
  integrations.py    — FortiGate / FortiWeb / Check Point
  store.py / cli.py  — конфіг і CLI
data/                — синтетичні логи для тестів
nginx/flyguard.conf  — reverse proxy (HTTPS, доступ лише з внутрішньої мережі)
```
